# Calendar automation

Calendar automation enrols eligible events from explicitly selected, connected accounts into the existing assistant scheduling and post-meeting workflow. It is opt-in per person and workspace. Installing this release does not enable joining, email, or knowledge-base inclusion for anyone.

## Configure the workflow

1. Connect calendar accounts under **Calendar → Integrations**. Only accounts belonging to the signed-in person can be selected for their rule.
2. Open **Calendar → Automation** and select the accounts to monitor. Connecting another account later does not automatically include it.
3. Choose one-off meetings, recurring meetings, or both. Choose either existing upcoming and newly discovered events, or newly discovered events only. Set the assistant name and acknowledge recording disclosure.
4. Choose the MOM format, optional focus fields, and drafting instructions. The default outcome is a draft for manual review.
5. Optionally enable automatic delivery. An owner or admin must first authorize this at workspace level and select allowed internal teams. The individual rule then selects recipients from those authorized teams. Create teams, such as Leadership, under Organization & people.
6. Knowledge inclusion is off by default. Optionally select one accessible knowledge base, or leave it off and assign a completed meeting later.
7. Use **Preview matches** to inspect the unsaved rule without creating assistants or sending email. Save the rule, then use **Check now** for an immediate check. Background discovery continues while enabled.

```text
Selected connected calendars
  → eligibility and duplicate checks
  → saved schedule for each eligible occurrence
  → assistant requests admission at the scheduled time
  → host admits or rejects it
  → transcript capture and existing automatic departure
  → automatic MOM draft
  → optional authorized team email
  → optional knowledge-base inclusion, now or later
```

The assistant does not bypass meeting admission or recording requirements. A calendar end time is not an unconditional recording cutoff: the existing leave watchdog handles departure when a call ends or is empty.

## Discovery semantics

- Discovery checks the next **14 days** and ignores events that have started or start within one minute. Schedule short-notice calls manually.
- A recurring occurrence is scheduled independently; future occurrences enter the rolling window over time.
- **Newly discovered** is a discovery baseline, not a claim about the provider's event creation time. The first complete scan records existing occurrences without scheduling them. Only later discoveries are eligible. An incomplete scan cannot establish that baseline.
- Invites declined by the connected person are excluded. Events need a supported meeting link and usable schedule metadata.
- A stored occurrence claim prevents repeated imports across scans, moves, restarts, or host rejection. Explicitly skipped or cancelled occurrences are not automatically resurrected.
- Existing call-coordination checks prevent a second assistant when the same call is already covered. Automatic enrolment never silently chooses the “own assistant too” option.
- A pass schedules at most **50** new occurrences, processing selected accounts in order and nearer events first within each account. Additional occurrences are deferred, not discarded.
- Unsupported or ambiguous provider metadata can exclude an occurrence. Review preview and scan messages; manual scheduling remains available.

## Permissions and delivery safety

Members can configure their own calendars and assistants. Viewers cannot enable automation. Only workspace owners and admins can authorize automatic delivery and its allowed teams. One person's rule cannot read another person's calendar or configure another workspace.

Automatic delivery uses internal teams containing active workspace members. External team addresses and calendar invitees are not automatic recipients. Existing manual delivery remains available for explicitly chosen recipients.

Email requires a completed, admitted capture, usable finalized transcript, and a MOM generated by the automatic workflow from the current transcript. Existing historical or manually created MOMs are not automatically sent on upgrade. Human MOM edits, regeneration, approval, sending, and explicitly stopping an assistant require manual review rather than continuing unattended delivery.

The recipient audience is frozen when automatic delivery is prepared. Retries reuse that audience and the original approval, rather than broadening distribution after a team changes. Membership, current workspace authorization, and the rule owner's permissions are checked again. Changed or invalid recipients and stale content hold delivery for review. Retries are bounded and stop within the email provider's idempotency window; uncertain delivery must be reviewed rather than retried indefinitely.

## Exceptions and stopping automation

- **Skip this occurrence** cancels its pending automatic join. It does not stop an active recording and cannot be undone into a new automatic join; schedule manually if needed.
- **Require manual review** holds that meeting's automatic email without disabling recording or MOM generation.
- Turning off personal automation cancels pending automatic joins and unattended delivery. Active recordings continue; saved meetings are retained.
- Removing selected accounts prevents further enrolment and revokes their pending automatic actions.
- Turning off workspace automatic delivery blocks unattended email, without disabling draft generation or calendar scheduling.
- Workspace and personal off switches remain available even when previously selected teams or knowledge bases have become invalid.

## Add a completed meeting to knowledge later

Open a meeting you own (or manage as a workspace admin) and use its AI knowledge settings. Choose an accessible knowledge base and enable inclusion. This queues indexing of the saved transcript and, when available, approved minutes. It does not reconnect to the meeting, fetch a fresh recording, or regenerate/change an already sent MOM. Changing the base updates retrieval ownership; opting out removes that meeting's indexed sources. Existing knowledge-base access rules still apply.

Saved content is subject to retention and deletion policies. A deleted transcript cannot be recovered by opting in later.

## Runtime and API

Required existing services: API, PostgreSQL, Vexa capture stack, configured transcription/text providers, Composio-connected calendars, and Resend for email. No new external provider key is introduced by automation.

| Setting | Purpose |
| --- | --- |
| `AUTO_CALENDAR_SCHEDULE_ENABLED=1` | Enables the existing scheduler/watch loop and new discovery worker. |
| `AUTO_MOM_ENABLED=1` | Enables automatic drafting and unattended delivery reconciliation. |
| `CALENDAR_AUTOMATION_SCAN_SECONDS` | Discovery cadence, default 300 seconds, bounded to 60–3600 seconds. |

The control screen reports server availability separately from saved preferences. An enabled preference cannot operate when its server worker is disabled. Discovery and delivery reuse the existing worker-leadership arrangement; do not independently run duplicate uncoordinated workers.

| Endpoint | Purpose |
| --- | --- |
| `GET/PUT /v1/calendar/automation` | Read/save the current person's rule. |
| `POST /v1/calendar/automation/preview` | Read-only preview of supplied settings. |
| `POST /v1/calendar/automation/reconcile` | Reconcile the saved rule immediately. |
| `GET/PUT /v1/workspace/automation-policy` | Read/admin-authorize automatic delivery. |
| `GET/PATCH /v1/meetings/{id}/automation` | Inspect or override an owned/managed automated meeting. |

Database schema **37** adds automation rules, policy, occurrence claims, meeting provenance/overrides, and durable automatic delivery state. Tables are additive; no existing calendar or meeting is opted in by migration. Back up the database before production rollout. An older API does not accept a newer schema version, so rollback requires a compatible application release or a deliberate database restore—not simply deploying the old image against schema 37.

## Validation boundaries

Automated tests use fake calendar, transcription, model, and email providers. They cover permission boundaries, defaults, recurrence discovery, duplicate suppression, cancellation, retries, delivery authorization, and late knowledge indexing. Browser tests cover the new controls and responsive layouts. Passing these checks is not a claim that a real Google/Outlook authorization, host-admitted call, or external email has been exercised. Validate those separately with consenting test participants before enabling real unattended delivery.
